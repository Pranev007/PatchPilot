# PatchPilot

**An agentic system for test-verified dependency migration.**

PatchPilot upgrades Python packages from 3.8 to 3.12 and proves it worked: the
repository's own test suite is the acceptance criterion, not the model's
opinion of its patch.

The agent reads a repository, edits it, and stops. The harness then runs that
suite and compares the result against a baseline captured before the migration
began. If any test that passed on the old interpreter no longer passes, the
failures go back to the agent and it tries again — up to an iteration cap and a
hard dollar cap.

The point of the project is that second half. "The model wrote a plausible
patch" is not a result. "N of M repositories reach a green test suite, at
$X per repository" is.

### The failures are budget, not defeat

Not one repository exhausted its *iteration* cap. All five failures hit the
**spend** cap, set at $0.30-$0.50 because the whole benchmark ran on a $5
budget. They ran out of money, not out of ideas.

How much that matters is measurable, so it was measured. Capped repos were
re-run with nothing changed but the cap:

| Repo | $0.30 cap | $0.42 cap |
|---|---|---|
| `mahmoud/boltons` | capped at 3 iters | **green in 4** |
| `agronholm/typeguard` | capped at 3 iters | capped at 3 iters |
| `pytoolz/toolz` | capped at 1 iter | capped at 1 iter |
| `PyCQA/pycodestyle` | capped at 1 iter | capped at 1 iter |

A 40% larger budget converted **one of four**. The failures are therefore not
uniformly a dollar short: `boltons` was genuinely close, while `toolz` and
`pycodestyle` burned an entire budget inside a single iteration both times
and never reached a second test run. For those, more budget buys more
exploration rather than more progress.

`Delgan/loguru` (1,328 tests) and `python-attrs/attrs` (1,161) were never
given a realistic budget -- their baselines alone take minutes and their
failure digests are large. They stay in the denominator rather than being
quietly dropped.

### What the cost distribution says

Successful migrations were cheap -- $0.019, $0.060, $0.091, $0.109, $0.372,
$0.380 -- and every failure burned its entire cap. When this agent can solve
a repository it does so in a median of 2 iterations; when it cannot, the
money goes on looking around. That asymmetry is the practical finding: for
this task a *low* per-repo cap across more repositories buys more successful
migrations per dollar than a high cap across fewer.

One caveat on the cap: it is checked before each model call, so a single
expensive call can overshoot it. Two repos ran to $0.46 against a $0.42 cap.
It bounds spend, it does not pin it.

## Worked example: `pallets/itsdangerous`

One repository end to end, so the loop is legible without reading the code.
Artifacts: [`runs/published/benchmark/pallets__itsdangerous/`](runs/published/benchmark/pallets__itsdangerous/).

> Every line below is recorded output from a real run — baseline, failure,
> patch and result. Nothing is reconstructed or illustrative.

### 1. Baseline on Python 3.8

The suite is captured before anything is touched:

```
exit=0 collected=297 passed=297 failed=0 skipped=0
```

297 test node IDs go into the baseline set. Those, specifically, are what must
still pass afterwards.

Note the install recipe this needed. `uv pip install -e .` alone collects tests
and runs **zero** of them — the suite imports `freezegun`, which lives in
`requirements/tests.txt`. The repo's own `tox.ini` says
`deps = -r requirements/tests.txt`, which is exactly why the selection filter
insists the CI config is the build recipe.

### 2. Switch to Python 3.12 — collection breaks

Same checkout, new environment. pytest cannot even finish collecting:

```
exit=2 collected=66 passed=0 failed=0 skipped=0
```

```
ERROR collecting tests/test_itsdangerous/test_timed.py
tests/test_itsdangerous/test_timed.py:7: in <module>
    from freezegun import freeze_time
.venv/lib/site-packages/freezegun/api.py:16: in <module>
    from dateutil import parser
.venv/lib/site-packages/dateutil/tz/tz.py:37: in <module>
    EPOCH = datetime.datetime.utcfromtimestamp(0)
E   DeprecationWarning: datetime.datetime.utcfromtimestamp() is deprecated and
    scheduled for removal in a future version. Use timezone-aware objects to
    represent datetimes in UTC: datetime.datetime.fromtimestamp(timestamp,
    datetime.UTC).
```

Worth reading the chain carefully, because it is the whole thesis of the
project in one traceback:

1. `datetime.utcfromtimestamp()` is deprecated in Python 3.12 — the canonical
   3.12 migration.
2. The call is not in `itsdangerous`. It is in `dateutil`, pulled in
   transitively by `freezegun`, pinned by `requirements/tests.txt`.
3. It is fatal rather than noisy only because the repo configures warnings as
   errors.

So the failure is real, is caused by the interpreter upgrade, and lives in a
*pinned dependency* rather than in the package under test. That is squarely in
scope — "dependency versions incompatible with the new interpreter" — so the
harness hands it to the agent instead of skipping the repo.

### 3. What the agent receives

No test executed at all, so the digest leads with the traceback rather than
naming 297 tests individually:

```
The test suite does not run on the new interpreter at all
(exit=2, 0 of 297 baseline tests executed). Fix this before anything else.

Output:
<traceback above>
```

Listing every baseline node ID here would bury the one traceback that explains
the failure, and would cost those tokens again on every iteration.

### 4. The patch the agent produced

Two iterations, 21 tool calls, **$0.109**:

```diff
--- a/requirements/tests.txt
+++ b/requirements/tests.txt
@@ -21,7 +21,7 @@ pyparsing==3.0.7
 pytest==7.0.1
     # via -r requirements/tests.in
-python-dateutil==2.8.2
+python-dateutil==2.9.0.post0
     # via freezegun

--- a/setup.cfg
+++ b/setup.cfg
@@ -39,6 +39,7 @@ testpaths = tests
 filterwarnings =
     error
+    ignore:datetime.datetime.utcfromtimestamp\(\) is deprecated:DeprecationWarning:dateutil.tz.tz
```

It found the actual cause rather than the symptom: the deprecated call is in
`dateutil`, so it bumped that pin — exactly the class of fix the scope
instructions describe. The `filterwarnings` line is belt-and-braces, narrowly
scoped to that one warning in that one module, and arguably redundant once the
pin moved. A reviewer might trim it; it does not suppress anything else.

### 5. Result

```
iteration 1  exit=2 collected=66  passed=0    <- suite would not collect
iteration 2  exit=0 collected=297 passed=297  <- all 297 baseline tests pass
```

Green. Every test that passed on Python 3.8 passes on 3.12, which is the only
claim this project is willing to make.

## What the failures look like

Built from the published `trace.jsonl` files, which record every tool call and
every test run. This is the section that changed my mind about what the agent
is actually bad at.

**Successes and failures do not differ in effort. They differ in shape.**

| | Tool calls | `run_command` share |
|---|---:|---:|
| `scrapy/w3lib` (green) | 2 | 0% |
| `pyeve/cerberus` (green) | 8 | 0% |
| `pallets/click` (green) | 13 | 0% |
| `pytoolz/toolz` (capped) | 30 | 47% |
| `python-attrs/attrs` (capped) | 37 | 62% |
| `agronholm/typeguard` (capped) | 43 | 40% |

A successful migration is small and quiet: read the traceback, edit the pin,
stop. `w3lib` took **two** tool calls. Failures are the opposite -- dozens of
calls, roughly half of them `run_command`, plus five to eight `write_file`
calls that are not edits at all but scratch scripts the agent writes, runs and
then deletes. One trace ends with the agent reporting that it "cleaned up the
scratch files".

So the tool surface is the problem, not the reasoning. `write_file` plus
`run_command` together make an ad-hoc REPL, and once the agent starts using
them that way it explores instead of editing. Tightening `run_command`'s
description helped (63 calls to 27 on the calibration repo) but did not stop
it. The next change is structural rather than prompt-level: no general shell
at all, only narrow tools that cannot be composed into one.

**Large suites die in the first iteration.** `loguru` (1,352 collected) and
`attrs` (1,180) each spent an entire budget before reaching a second test run.
With hundreds of failing tests the digest is enormous, it is re-sent on every
turn, and the agent never gets a second attempt. Repository size drives cost
far more than repository difficulty -- which argues for truncating the digest
by failure *class* rather than by count.

**One "failure" was the harness's fault, and the agent was right.**
`humanize` reported four regressions that no patch could fix, because its
parametrized test IDs embed a memory address. The agent investigated, concluded
the failures were "a false signal", and said so in its final reply. The harness
overruled it and recorded a failure. It was the harness that was wrong:
`humanize` migrates cleanly and has now been removed from the set entirely.
Worth sitting with — the agent's judgement beat the oracle's, and only reading
the trace surfaced it. See [Verifying the verifier](#verifying-the-verifier).

**One failure was making real progress when the money ran out.** `typeguard`
went from a suite that would not run at all, to 19 tests collected, to 243
collected with 205 passing, across three iterations -- then hit the cap. That
is not a capability failure, and the results table says so.

## Effort sweep

Reasoning effort trades dollars for capability, and the useful question is not
"is more better" but "where does more stop paying". `patchpilot sweep` runs the
whole benchmark at several effort levels and plots the answer.

```bash
patchpilot sweep --efforts medium high xhigh --repeats 3 --max-total-spend 20
```

It writes `SWEEP.md`, `sweep.csv` (one row per repo run, so the sweep can be
re-analysed without re-running it), and `sweep.png`.

> **Not yet run.** A sweep at three effort levels with `--repeats 3` is
> 108 repository runs -- roughly nine times the benchmark above, or about $30
> at the observed cost. The $5 budget went on the single-effort benchmark and
> the cap-sensitivity experiment instead, on the grounds that one honest number
> plus one controlled comparison beats a sweep too underpowered to read.
> The machinery is built and tested; it needs budget, not code.

**`$/success` is usually the number to decide on.** It divides total spend —
including everything burned on repos that never went green — by the repos that
actually landed. A cheaper level that fails more often can easily cost more per
repo delivered, and the median-cost column alone hides that.

Three things the sweep does deliberately:

- **`--repeats` gives an error bar.** The agent is nondeterministic. One run
  per level is a point estimate with no spread, which invites reading noise as
  a trend. With fewer than about 15 repos the error bars will overlap heavily —
  that is the honest result, and it means you cannot yet distinguish the
  levels. The chart prints its own sample size for exactly this reason.
- **It states worst-case spend before starting** and stops cleanly at
  `--max-total-spend` rather than presenting the bill afterwards.
- **It resumes.** Every cell writes `result.json` as it completes, so a crash
  or a Ctrl-C costs one cell, not the afternoon:

```bash
patchpilot sweep --sweep-dir runs/sweep-2026-08-19T10-00-00 --resume
```

Regenerate the table, CSV and plot from a finished sweep without re-running:

```bash
patchpilot sweep-report --sweep runs/sweep-2026-08-19T10-00-00
```

## Providers

The verify loop, harness and sandbox do not care which model wrote the patch,
so the model sits behind a narrow provider boundary. Anything that speaks the
OpenAI Chat Completions protocol works through one implementation:

| `--provider` | Endpoint | Key read from |
|---|---|---|
| `anthropic` (default) | Anthropic API | `ANTHROPIC_API_KEY` |
| `gemini` | Google AI (OpenAI-compat) | `GEMINI_API_KEY` |
| `deepseek` | DeepSeek | `DEEPSEEK_API_KEY` |
| `openrouter` | OpenRouter | `OPENROUTER_API_KEY` |
| `together` | Together AI | `TOGETHER_API_KEY` |
| `huggingface` | HF Inference Providers | `HF_TOKEN` |
| `openai` | OpenAI | `OPENAI_API_KEY` |

Anything else works with `--base-url`. Keys are read from the environment and
never accepted as arguments — a key passed on the command line lands in shell
history and in the process list.

```bash
patchpilot run --provider gemini   --model gemini-2.0-flash
patchpilot run --provider deepseek --model deepseek-v4-flash
```

The Anthropic path keeps features the compatibility layer cannot express:
adaptive thinking, reasoning effort, explicit prompt-cache breakpoints and
server-side fallbacks. On other providers `reasoning_effort` is sent
optimistically and dropped on first rejection, so `--effort` is a no-op where
it is unsupported — which is why the sweep's natural axis there is **model**
rather than effort.

### The no-op-turn guard

Some models end a turn describing an edit instead of performing one. Without a
guard the harness treats that as a completed attempt, re-runs an unchanged
checkout, sees identical failures, and burns an iteration — six of those and a
repo is reported as `failed_iterations` when the model never actually failed
the migration, only the protocol.

A turn that calls no tools is therefore re-prompted rather than counted, twice,
then the iteration ends. `noop_retries` is recorded per repo, so a model with a
protocol problem is visible in the results rather than mistaken for a model
with a capability problem.

## How it works

```
  clone repo @ pinned ref
        |
  venv on Python 3.8  ->  install  ->  pytest  ->  BASELINE (set of passing test IDs)
        |
  swap venv to 3.12   (same checkout: only the interpreter changes)
        |
  +---> install -> pytest
  |         |
  |     regressions vs baseline?  --no-->  SUCCESS
  |         | yes
  |     hand failures to the agent, it edits files
  +---------+                              (max 6 iterations, or $1.00)
```

| Module | Role |
|---|---|
| `harness.py` | The oracle. Baseline capture, per-test outcome parsing, regression comparison. |
| `runner.py` | The verify loop and the outcome taxonomy. |
| `agent.py` | The conversation: a hand-written tool-use loop. |
| `sandbox.py` | Where code runs. Local-venv and Docker backends behind one interface. |
| `tools.py` | The five tools the agent gets. |
| `ledger.py` | Tokens, dollars, tool calls, and a JSONL trace per repo. |
| `report.py` | Turns `result.json` files into the table above. |
| `sweep.py` | Runs the benchmark across effort levels; budget, resume, plot. |
| `providers/` | Anthropic and OpenAI-compatible backends behind one interface. |

## Running it

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv -e .
```

Set a key for whichever provider you are using (see
[Providers](#providers)). Export it in your own shell — never pass it as an
argument:

```bash
export ANTHROPIC_API_KEY=...
```

Check the environment before spending anything:

```bash
patchpilot doctor
```

Validate a repository without calling the model at all — `--max-iterations 1`
establishes the baseline, runs the first test pass, and stops. It costs $0.00
and tells you whether the harness can drive that repo:

```bash
patchpilot run --only pallets/itsdangerous --max-iterations 1
```

Then the real thing:

```bash
patchpilot run --sandbox docker --effort xhigh
patchpilot report --run runs/2026-08-17T23-13-06
```

## Methodology

Four decisions do most of the work of keeping the number honest.

**Success is "no regressions", not "all tests pass."** Repositories ship with
tests that were already failing, tests that are skipped on some platforms, and
tests that are flaky. Requiring a fully green suite would penalise the agent
for breakage it never caused. The harness records the *set of passing test node
IDs* before the migration and requires that set to still pass afterwards.

**A baseline needs at least one passing test, not just a collection count.**
pytest reports a collection count even when an import error stops the run
before a single test executes. Gating on `collected > 0` accepts that as a
baseline with an empty passing set — and then every later run is trivially
regression-free, so a repository the harness never tested gets reported as
successfully migrated. This was a real bug during development; there is a
regression test for it in `tests/test_harness.py`.

**Skips are reported separately from failures.** `skip_no_baseline` and
`skip_install` mean the harness could not establish ground truth. Folding them
into the denominator understates the agent; folding them into the numerator
overstates it. They get their own rows, and the headline rate is quoted over
attempted repositories with the skip count stated next to it.

**The sandbox interpreter is verified, not assumed.** After every environment
setup the harness asserts the interpreter really is the version requested.
Without that check a misconfigured sandbox falls through to the host Python:
every repository still builds, every test still runs, and the benchmark
reports a number that measures nothing. That is a worse failure than crashing,
because it looks like a result.

### What the benchmark measures

`--honour-test-pins` selects between two different questions:

- **Default** — pytest is forced to a current release, overriding the repo's
  pin. Measures migration of *the package*, with the test runner held
  constant.
- **`--honour-test-pins`** — the repo's own pins are respected. Measures the
  package *and its test tooling*, which is what a real upgrade involves. More
  faithful, noisier, more expensive.

Either is defensible. Reporting a number without saying which one you used is
not.

### What selection actually cost

36 candidates were scouted to get these 11. The rejections are the
interesting part:

- **15 were already green on 3.12** and were dropped. Every one was tagged in
  2020–2022, before 3.12 existed — `jinja`, `idna`, `mistune`, `xmltodict`,
  `funcy`, `tenacity`, `cachecontrol`, `chardet`, `jsonschema`, `colorama`,
  `thefuzz`, `webcolors`, plus `zipp`, `more-itertools` and `humanize`. They
  would have scored as free successes.
- **10 could not be baselined or built** here and were dropped.

The last three of those fifteen are worth dwelling on. `zipp`,
`more-itertools` and `humanize` all sat in the benchmark for a while,
apparently failing on 3.12. None of them were failing. `pytest-json-report` reports `unittest.subTest` results as
`"subtests passed"` rather than `"passed"`, the parser recognised only the
latter, and those results were silently dropped — so `zipp` showed 35 passing
on 3.8 against 8 on 3.12 while the suite exited 0 both times. `humanize`
failed differently: its parametrized test IDs embed a memory address, so two
identical runs disagree about which tests exist. Three repositories sat in the
benchmark on the strength of regressions that never happened, and `humanize`
was scored as an agent *failure* while it was there. See
[Verifying the verifier](#verifying-the-verifier).

The lesson worth keeping: **"tagged before 3.12 existed" does not predict
"needs migration for 3.12."** Pure-Python libraries are largely
forward-compatible. What actually breaks a repo is a *pinned dependency* that
does not survive the interpreter jump — exactly the pinned-`dateutil` case in
the worked example above. A third of a plausible-looking candidate list had no
migration work in it at all, and only running the validation pass revealed
which third.

The other recurring cost was test-only dependencies. Thirteen repos collected
tests but ran zero because something like `hypothesis`, `cherrypy`, `tornado`,
`freezegun` or `pytest-benchmark` was missing. Each was read off the collection
error and added to `install` — six of those became admissible repos.

## Verifying the verifier

A harness that decides whether a migration worked can be wrong in two
directions, and both are worse than crashing because they produce a confident
number instead of an error. Each of these was a real bug, caught by running the
thing rather than by reading it:

**False green — a repo reported as migrated that was never tested.**
`pytest` prints a collection count even when an import error stops the run
before a single test executes. Gating the baseline on `collected > 0` accepted
that as a valid baseline with an empty passing set, after which every later run
was trivially regression-free. The gate is now "at least one test actually
passed".

**False failure — regressions invented out of a vocabulary mismatch.**
`pytest-json-report` reports `unittest.subTest` results as `"subtests passed"`,
not `"passed"`. The parser recognised only the latter and silently discarded
the rest. Because the two interpreters can resolve different plugin versions,
the *same repo* reported `passed` on 3.8 and `subtests passed` on 3.12 — so the
comparison manufactured regressions that never happened. `jaraco/zipp` showed
35 passing against 8 with the suite exiting 0 both times, and sat in the
benchmark set for two commits on the strength of it. Unrecognised outcomes now
go to an `unknown` bucket that appears in the summary, because a dropped result
is indistinguishable from a test that vanished.

**Wrong interpreter — a benchmark measuring nothing at all.**
A relative sandbox path combined with the subprocess working directory created
the virtualenv one level too deep. Everything downstream then fell through to
the host Python: every repo still built, every test still ran, and the numbers
looked entirely plausible. The interpreter is now asserted after every
environment setup, and a mismatch aborts the run.

**Non-deterministic node IDs — an oracle that disagreed with itself.**
When a parametrized fixture has no custom repr, pytest names the case after the
default object repr, which contains a memory address:

```
test_naturaldate[test_input7-<tests.test_time.FakeDate object at 0x283E5B81100>]
```

That address changes every process, so running the *same suite twice with no
changes* produced four different node IDs. `humanize` was therefore unwinnable:
four phantom regressions no patch could fix. The agent worked it out, reported
the failures as "a false signal", and was overruled by the harness. IDs are now
normalised before comparison, and `humanize` — which migrates cleanly — has
been removed from the benchmark set.

Two more surfaced only against a live provider:

**Gemini 3.x multi-turn tool use was impossible.** The model attaches a
`thought_signature` to each function call and rejects the following request
without it. Rebuilding assistant messages from only the recognised fields broke
every repo on its second API call. Provider extension data is now echoed back
verbatim.

**The effort sweep compared nothing.** The provider factory closed over the
CLI's `--effort`, so every cell would have run at the same effort while the
table and chart claimed otherwise. It now derives from the per-cell config.

The pattern is consistent: the dangerous failures are the quiet ones. Four of
these six produced results that looked entirely plausible and meant nothing,
which is exactly the failure mode this project exists to rule out — so the
harness now fails loudly instead, and unrecognised or unstable inputs are
surfaced rather than silently absorbed.

It is also worth naming what this cost. Three repositories were in the
benchmark set on the strength of regressions that never happened, and one of
them was scored as an agent failure for two commits. Every one of these bugs
was found by *running* the harness and reading traces — none by reading the
code.

## Selecting repositories

The filter used to build the set above:

1. **The repository tells you how to build and test it.** A working GitHub
   Actions workflow or `tox.ini` *is* the build recipe — copy `install` and
   `test` straight out of it. Repos that don't document this get skipped;
   chasing undocumented system dependencies is not what you are measuring.
2. **`install` must include test-only dependencies.** `pip install -e .` alone
   is usually not enough. `itsdangerous` at `2.1.2` collects tests and runs
   zero of them without `requirements/tests.txt`. Thirteen of the 36 scouted
   candidates failed this way.
3. **Pin `ref` to a commit or tag from before the repo supported 3.12.** Check
   that the CI matrix at that ref caps at 3.8 or 3.9. If the code already runs
   on the target there is nothing to migrate.
4. **Small, pure Python, fast suite, no network, no database.**

Fifteen repositories with a rigorous harness beat fifty aspirational ones.
Validating one costs nothing, so there is no reason to guess:

```bash
patchpilot run --only <name> --max-iterations 1
```

## Known limitations

- **The local sandbox is not isolated.** `--sandbox local` runs repository
  build scripts and test suites on your machine as you. It exists so the
  project runs without Docker for hand-picked repos you have read. Use
  `--sandbox docker` for anything else.
- **Python and pytest only.** The oracle depends on `pytest-json-report` for
  per-test node IDs. Other runners need a new parser.
- **One migration lane.** 3.8 → 3.12 with deprecated-stdlib and dependency-pin
  fixes. The scope is enforced by the system prompt, not by anything
  structural, so the agent can still wander.
- **One attempt per repository, so the results have no error bar.** The agent
  is nondeterministic and 11 repos is a small sample: 6/11 could plausibly be
  4/11 or 8/11 on a re-run. `patchpilot sweep --repeats N` exists for this and
  has not been run -- it needs roughly 3x the budget this benchmark had.
- **The published numbers mix two spend caps** ($0.30-$0.50), because the
  budget was fixed and the cap was the variable being explored. The per-repo
  cap is in the results table for that reason. A clean headline needs one cap
  across all repositories.
- **No held-out set.** The prompt was revised once during this benchmark (the
  cost fix in `949e27c`) using the same repositories now being reported on,
  which is mild overfitting. Split the set before quoting the number
  anywhere it matters.
- **No held-out set.** Tuning the prompt against the same repos you report on
  overfits. Split them before you publish a headline number.
